# Test suite — what runs, what doesn't, and why

## The two commands

```
cd Verilog
make test        # every self-checking unit testbench, FAIL-FAST
make test-full   # adds the heavy system gates (latch-vs-FF golden trace,
                 # runSim golden console, Tang vtest boot+deposit)
```

**Fail-fast matters:** the first failure aborts the run. Green means "green up
to the first failure" — it does not mean everything after it also passed. When
something fails, fix it and re-run; do not assume the rest of the suite is fine.

## The registry

`run_all_tests.sh` holds one line per entry:

```
<dir relative to Verilog/> :: <make target> :: <required pass pattern>
```

An entry fails when the target exits nonzero, when its output contains a FAIL
line, or when the required pattern is absent. **The pattern must be strict** —
`TB_RESULT: PASS` by convention. A test that can pass silently can fail
silently, which is why a testbench without a machine-checkable verdict cannot
be registered at all.

## Coverage, measured

Run `make catalog` in this directory for the live numbers (testbench sources,
how many `make test` reaches, orphans, modules with and without a testbench).
The generated result is `TESTBENCH-CATALOGUE.md`; no count is kept in this
README because a copied number goes stale the day a testbench is added.

Counts used to be guessed. A count of registry lines is *not* a count of
testbenches run — one entry can run several testbenches (the `iv-%` pattern
rules do exactly this), and a testbench can sit in the tree with nothing
pointing at it. `tb_catalog.py` resolves each registry target through its
Makefile — prerequisites, recipe lines, aggregate targets, pattern rules and
expanded variables — to find what is really executed.

## The orphan gate

`make test-tb-catalog` (registered as the first entry in the suite) fails if a
testbench exists that neither the registry reaches nor `ORPHAN_BASELINE` in
`tb_catalog.py` excuses. Writing a testbench and forgetting to register it is
now a build failure, not a silent loss.

The baseline may only **shrink**. Every entry carries a specific reason, and
that reason in `tb_catalog.py` is the one live list - read it there (there were
17 entries on 28-SEP-2026). They fall into these groups:

- **Detectors and reproducers for open faults** - deliberately red against
  today's RTL (for example the CGA_TRAP TVGEN trap-vector timing benches and
  `F595_transparency_tb.v`). The suite is fail-fast, so a red test would block
  every later one; each is registered the day it goes green.
- **Unresolved or parked** - red for a reason not yet established, or waiting
  on another workstream (for example `CGA_MAC_pt_apt_selection_tb.v`,
  `nd_storage_smd_adapter_tb.v`, `sd_fat_block_tb.v`).
- **No machine-checkable verdict** - cannot be gated as written
  (`MASEL_cycle_tb.v`, `MASEL_iw_capture_tb.v`), or a verdict that is red for
  a check-count reason still to be explained (`DECODE_DGA_COMM_tb.v`).
- **Board bring-up harnesses, not unit tests** (`basys3_mem_test_tb.v`,
  `qmtech_mem_test_tb.v`, `sd_fat_test_tb.v`, `nd120_tang20k_tb.v`).

## Untested modules

`UNTESTED-MODULES.txt` is regenerated by `make catalog`. It is a **backlog, not
a failure** — this project has built testbenches where bugs were found rather
than uniformly, and an untested module mostly means a module that has never
misbehaved. Use it to pick targets when a subsystem starts acting up, not
as a number to drive to zero.

## Adding a testbench

1. Put it in the module's own `sim/` directory — there is no central test tree.
2. Make it print `TB_RESULT: PASS` or `TB_RESULT: FAIL <n> errors`.
3. Add a make target in that `sim/Makefile`.
4. Register it in `run_all_tests.sh` with a strict pass pattern.
5. Run `make test-tb-catalog` to confirm it is reachable.

Step 5 is the one that used to get skipped.
